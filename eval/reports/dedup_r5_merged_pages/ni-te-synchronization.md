## Overview

Ni-Te synchronization describes the execution failure in which **vision generation outpaces execution architecture**: Ni floods the problem space with complexity and possibility faster than Te can select from it or build into it. The gap widens, Te loses its Ni direction, the project becomes motion without vector, and the sequence terminates either in Se escape as a release valve or in somatic freezing before any external action is taken. This is not a willpower failure or an inability to do the work — the vision is present, often overwhelming in detail and scope — but the bridge between it and concrete next actions collapses under complexity. The two source accounts differ in scope and are held in tension: the more recent framing extends the pattern to both Ni-dominant (INTJ) and Ni-auxiliary (ENTJ) types, while the earlier one treats it as INTJ-specific and argues that the mechanism *depends* on Te being auxiliary — Te fires episodically and therefore lacks the continuous governor that dominant Te supplies, so an ENTJ's Te-saturation surfaces instead as prioritization failure.

## Notes

**The failure sequence**

1. Project complexity grows beyond a threshold where the next action is ambiguous.
2. Ni continues generating patterns and implications faster than Te can implement; Ni operates as a continuous synthesis engine with no built-in throttle.
3. Te, without a clear Ni output to execute against, either begins running on Se — action for its own sake (the [[concepts/entj-te-se-loop]]) — or applies itself to *organizing* Ni output rather than routing it outward.
4. Alternatively, Te stalls entirely and Ni loops back into Fi: private conviction without reality-testing (the [[concepts/ni-fi-loop]]).
5. Se escape activates as a release valve — binge-watching, compulsive scrolling, passive consumption.

**Scope explosion.** When Te lacks a pre-committed external target, the result is an ever-expanding architecture of notes, plans, and synthesis documents that recirculate rather than discharge (see [[concepts/consolidation-as-displacement]]). Brian Cho's FEB_2025_notes are diagnosed in the source as a direct artifact of unchecked Ni: twenty-plus unrelated domains simultaneously generating connection patterns, with Te attempting to build organizational containers for all of them at once. The scope becomes civilizational before any single thread has been selected for execution. "Compulsively adding Te and Ni until overwhelming" is auxiliary Te without a governor, not Te-dominant behavior.

**The binge-watch is diagnostic, not a character defect.** It signals one of three things: the next action is genuinely undefined; cognitive load has exceeded capacity and real rest is needed; or Ni is processing something not yet surfaced. The problem is not the escape — it is not knowing which of the three applies.

**Relation to the Te-Se loop.** The Te-Se loop is a stress response — Te running hot without Ni direction. Ni-Te desynchronization is the upstream cause: the reason Te loses Ni direction in the first place. Resolving desynchronization prevents the loop from starting rather than recovering from it once active. It is likewise the upstream entry point of [[concepts/total-stress-collapse-sequence]].

**Interventions**

- *Commit Te to one external artifact before the Ni session opens.* Once a concrete output is pre-committed — a sent message, a published paragraph, a real decision delivered to a real person — Ni's synthesis flows toward it rather than proliferating. Any action that exports energy into the world discharges the loop; any action that adds structure to existing notes recirculates it. Musashi's "eliminate unnecessary action" is cited as the operative discipline: one Te target, then Ni runs.
- *Define the next physical action before ending any session.* One sentence beginning with a concrete verb, at artifact level, not a goal or a direction: *Open the file and write three bullet points describing what the graph query needs to return.* The specificity is the point — Te needs something to grip immediately without negotiation.
- *Separate modeling sessions from building sessions.* Modeling is Ni work (understanding the system, seeing what is needed); building is Te-Se work (executing against a decided direction). When building hits uncertainty, the wrong move is to start modeling inside the building session — that is where the loop starts. Stop the session, write down the question to be resolved, close the IDE, think on paper, resolve it, then return to building.
- *Complexity threshold triggers reduction, not addition.* The strong-Te instinct is to add structure — more organization, documentation, planning layers. This is almost always wrong. Complexity that stops execution signals that scope has outrun clarity. Find the smallest version that proves the core thesis (the 20% that validates 80%); everything else is Phase 2 or cut.
- *Name the cause before opening the escape hatch.* Before opening YouTube or equivalent, write one sentence: *I am stopping because ___*. Naming often resolves the stall — if the next action is undefined, naming it defines it; if genuinely depleted, naming it permits rest without guilt; if Ni is processing, naming it permits consuming without shame and returning.
- *One-question complexity audit before every session.* *What is the one thing that, if resolved today, would make tomorrow's work easier?* Not a list — one thing, to force the hierarchy. Ni resists this because it sees all the interdependencies.
