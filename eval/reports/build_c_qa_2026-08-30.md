## Q1. What is the Sumimasen intervention pattern and where does it apply?

### Lane A — parallel  _(OK, 43.4s, 6046ch)_

## What it is

**Sumimasen is a delivery gate, not a retrieval or ranking mechanism.** The core statement in `concepts/sumimasen` — which arrives truncated in this retrieval — is that "an AI system earns the right to interrupt by demonstrated utility rather than interrupting on a fixed schedule. Named after the Japanese expression of pol…" The page cuts off there, so the full definition is not directly readable in this window; the quoted continuation ("…polite apology/excuse-me — the AI announces itself only when it has genuine cause") appears only secondhand, inside `comparisons/R2_headless_vs_claude_ai_2026-08-27`, which is a record of a prior QA run rather than primary substrate.

The economic framing is consistent across pages: an interruption is a debit that must be covered. `concepts/strict-intervention-contract` states the asymmetry directly — "in a hospitality context (someone's conversation at a table), a false positive is socially costly: it trains the user to distrust or ignore the system."

## How it's implemented — two stacked gates

The 2026-08-02 MVP build (`sources/2026-08-02-ai-as-a-conversational-research-partner-dec921`) is described there as "the first concrete implementation record of the Sumimasen idea," and it splits the gate across two layers:

**1. Reticence control (upstream, deterministic).** Before Claude is queried at all, two conditions must clear: enough new words (~14+) and a natural pause (~2.6 s of silence). A tunable reserved/balanced/eager setting adjusts the word threshold and the cooldown between checks. The source page frames this as "a hand-coded instance of `concepts/timing-intelligence` and a direct design response to `concepts/action-friction`" — it "avoids the false-positive problem before it reaches the LLM."

**2. Strict intervention contract (LLM layer).** `concepts/strict-intervention-contract` inverts the model's default: it must return `{"interject": false}` unless one of three enumerated triggers is met — an unanswered factual question, a materially wrong factual claim, or a conversational stall caused by missing knowledge. The page is explicit about why enumeration matters: "enumerating the trigger conditions in the prompt — rather than asking the model to 'be careful' or 'only intervene when important' — produces more reliable behavior."

The two are described as complementary, not redundant: "reticence control reduces unnecessary API calls; the intervention contract ensures that queries that do reach the model produce minimal false positives" (`concepts/strict-intervention-contract`).

## Where it applies

**Ambient conversational listening — the built case.** Phone face-up at a café or in a car; a soft rin bell (three inharmonic sine partials) rather than speech; an andon-styled card the user pulls when ready. The source page names the push/pull split explicitly: "the chime is a push signal (unsolicited, ambient). Viewing the card is a pull action (user-initiated, low friction)" (`sources/2026-08-02-…-dec921`). Notably, the design *accepts* 5–15 s of web-search latency because the card only needs to arrive "while the topic is still warm."

**Generalization beyond Sumimasen.** `concepts/strict-intervention-contract` lists three transfer targets: a meeting assistant that surfaces only action items, a code review agent that must find a specific defect class to comment, and a notification agent that defaults to silence unless a time-sensitive event fires.

**Inside a deterministic notification stack.** `concepts/propose-dispose-pattern` is the structural home for this in an L4 setting: "the LLM proposes; the deterministic rules engine disposes." The LLM proposes an interruption level; token buckets, bloom-filter dedup, and delivery semantics remain outside its reach. Of its six compensating controls, two bear directly on a Sumimasen gate — *confidence-gated escalation* (cap output level by confidence) and *training-signal capture* (dismissals close the feedback loop).

**Measurement frame.** `concepts/jitai` supplies the academic vocabulary — decision points, tailoring variables, intervention options, decision rules — and names micro-randomized trials as the evaluation design, calling JITAI "the nearest academic field to MIKAI's surfacing problem."

### Lane B — serial  _(OK, 55.3s, 6416ch)_

## Sumimasen — the intervention pattern

### Core principle

Sumimasen is a **delivery gate whose default state is silence**. `concepts/sumimasen-gate` gives the canonical statement: *"default to silence; surface a suggestion only when redundancy is high AND confidence is high."* Interruption is not the normal operating mode that gets suppressed on bad inputs — it is the exception that must be affirmatively earned by two conditions holding simultaneously.

The name is load-bearing: the Japanese expression for a polite, minimally intrusive interruption. `entities/sumimasen-app` uses the same gloss.

### Why the gate is shaped this way

The justification in the substrate is **asymmetric trust cost**, stated in `concepts/sumimasen-gate`:

> "a false consolidation prompt … burns trust in the automation pipeline in a way that a missed suggestion does not."

False positives and false negatives are not symmetric errors, so the decision threshold is deliberately biased away from the midpoint. Everything else in the pattern — cooldowns, word thresholds, silence detectors, enumerated trigger lists — is downstream of that single asymmetry.

A secondary property: the gate is **cheap-first**. `concepts/sumimasen-gate` specifies that it "runs on cheap statistics before any LLM call, preventing unnecessary model invocations." The expensive judgment is only reached if the cheap one already passed.

### Two instantiations present in this vault

The substrate contains the pattern at two different layers, and they are specified quite differently:

**1. Statistical gate over a knowledge base** (`concepts/sumimasen-gate`). Conditions: cluster redundancy metric crosses a meaningful (non-marginal) threshold, AND the identity detector is certain the threads belong together. Applied inside `concepts/triggered-compaction`, where "every auto-proposal is a Sumimasen transaction."

**2. Reticence + contract over live conversation** (`entities/sumimasen-app`). A dual trigger fires only after **≥14 new words and ≥2.3 seconds of silence** — explicitly "avoiding mid-sentence interruption" — before ~1,600 characters are sent to Claude under "a strict three-condition intervention contract." Prior card titles are fed back into every prompt to suppress repetition. Output is a soft rin bell and a small card, never speech. Reticence is user-tunable across three modes (Reserved / Balanced / Eager), which shift the word threshold and cooldown.

Note the layering in the app: the silence-and-word-count test is a cheap statistical gate; the three-condition contract is the expensive one. That matches the cheap-first structure of the concept page, even though the two pages never cross-reference each other.

### Where it applies

Within these pages, four application sites:

| Site | Page |
|---|---|
| Thread-consolidation auto-proposals | `concepts/sumimasen-gate` → `concepts/triggered-compaction` |
| Ambient live-conversation surfacing | `entities/sumimasen-app` |
| Push-vs-passive decisions in the EA feed | `comparisons/R2_headless_vs_claude_ai_2026-08-27`, quoting `concepts/proactive-personal-intelligence-feed` |
| MIKAI's own S4 / delivery-gate layer | same comparison page, quoting `concepts/second-brain-strata` |

`concepts/sumimasen-gate` also places the pattern in a family: it is "the same family of mechanism as `concepts/jitai` … and `concepts/timing-intelligence`: an interruption-worthiness decision that weighs the value of the intervention against the cost of the interruption at the current moment." The gate instantiates that family for knowledge management rather than behavioral nudging. `concepts/timing-intelligence` independently frames this as "knowing *when* to surface information, not just what" — and calls it "the unsolved problem in all current executive assistant and personal AI products as of mid-2026."

`concepts/propose-dispose-pattern` is structurally adjacent — its "confidence-gated escalation" variant caps a learned layer's output by its confidence score, with low-confidence proposals suppressed — but that page never names Sumimasen, so the connection is mine, not the substrate's.

### Discrepancies and gaps in this vault

Three things I should flag rather than smooth over:

**The two definitions do not fully agree.** `concepts/sumimasen-gate` presents itself as the canonical definition and states the conditions in consolidation-specific terms (redundancy + identity confidence). That framing does not cleanly cover the conversational case in `entities/sumimasen-app`, where there is no "redundancy" quantity at all. The generalization from one to the other is implicit and undocumented here.

**A numeric conflict.** `entities/sumimasen-app` specifies a **≥2.3-second** silence trigger. The prior QA answer captured in `comparisons/R2_headless_vs_claude_ai_2026-08-27` reports **~2.6 s** from the parallel vault. These pages disagree; nothing here resolves which is current.

**Much of the richest material is secondhand.** The comparison page quotes `concepts/sumimasen`, `concepts/interruption-asymmetry`, `concepts/thread-state-machine`, `concepts/strict-intervention-contract`, and the V1 rules (48h cooldown, 7–30d stall window, cap 5/cycle, dismiss-rate <30% for 14 days). **None of those pages are in this retrieval.** They are quoted evidence from a parallel-vault answer, not primary pages I can verify here. Notably, the "gate on dismiss rate, not on confidence" prescription attributed to `concepts/interruption-asymmetry` directly *contradicts* the confidence-based condition in `concepts/sumimasen-gate` — I cannot adjudicate that from what I have.

**Silent on:** actual threshold values for "high redundancy" and "high confidence"; how trust is recovered after a false positive; and whether the pattern has ever been validated in the field. On that last point the substrate is candid — `queries/does-sumimasen-latency-break-conversational-warmth` records that the 5–20 second delivery window's "still warm" rationale is "assertion only — no test," and calls it "the single largest hypothesis the MVP needs to validate." `entities/sumimasen-app` puts the app at "prototype validated in claude.ai artifact as of 2026-08-02," standalone deployment unconfirmed.

So: a well-specified pattern with a clearly articulated justification, two concrete implementations, and no empirical validation of its central timing claim anywhere in these pages.

## Q3. How does the L4 task-state machine classify threads (exploring / decided / acting / stalled)?

### Lane A — parallel  _(OK, 52.6s, 6250ch)_

## Short answer

The substrate specifies **what the states are, what vocabulary the classifier operates over, and what kind of computation is allowed** — but it does not contain the classification rules themselves. There is no page in the retrieved set that states the conditions under which a thread is judged to be in one state versus another.

## What the pages do establish

**1. The state set is six, not four.** `concepts/mikai-l4-state-machine` gives the lifecycle as:

> `exploring → evaluating → decided → acting → stalled → completed`

`entities/mikai` repeats it with one word varying (`deciding` rather than `decided`). Your question names four; the substrate's canonical list includes `evaluating` and `completed` as well.

**2. Classification is the middle stage of a three-stage pipeline.** Both trigger modes run the same pipeline (`concepts/mikai-l4-state-machine`):

> **detect thread → classify state → infer next step**

The stated difference between an explicit trigger (button press) and an inferred one (the "shoe stall": user near a shoe store, browsed footwear three times, no intent stated) is *not* a different classifier — it is entry point and action license. "Explicit triggers enter later in the machine with more action license; inferred triggers enter at exploring with minimal license until the act/dismiss loop earns trust."

**3. Classification must be deterministic — no LLM.** This is the strongest constraint in the substrate, and it is asserted in three places:

- `concepts/thread-state-machine` calls the layer "a deterministic model," and scopes prioritization as "deterministic feature computation, not an LLM task (D-026 zero-LLM principle)."
- `entities/mikai`: "The orchestration layer bets on zero-LLM rule-based state classification (O-036)."
- `entities/mikai` also enumerates the only three roles LLM inference is permitted — Track A extraction, terminal desire synthesis, natural language delivery. State classification is not among them.

So the intended mechanism is rules over computed features, not model inference. (The two pages label the same commitment differently — `D-026` in one, `O-036` in the other — and the substrate does not reconcile those identifiers.)

**4. The classifier's input vocabulary is fixed and empirically chosen.** Per `concepts/mikai-l4-state-machine` and `sources/2026-06-18-task-state-awareness-2-0-b2f08c` (O-035 resolved), the spine is the activity vocabulary: **goal, constraint, candidate, comparison-criterion, stall-point, participant-preference**. The epistemic vocabulary (`unresolved_tension`, `contradicts`, `depends_on`) was "discarded as load-bearing for task state" after two hand-labeled scenarios "produced zero epistemic structures." Note that `stall-point` — "where and why forward progress has stopped" — is the one vocabulary term that directly carries state information.

The 2026-06-18 source records a falsifiable revival condition: "if O-036 (zero-LLM rule-based state classification) fails at scale, typed relational edges may return as necessary."

**5. The only numeric threshold anywhere in the retrieved set** is in the Sumimasen V1 rules quoted in `comparisons/R2_headless_vs_claude_ai_2026-08-27`, sourced from `sources/2026-04-02-agent-memory-640e67`:

> "48h cooldown per thread, 7–30d stall window, recency filter, cross-source boost, cap 5/cycle. Deterministic rules only at V1."

The "7–30d stall window" is the closest thing to an operational stall criterion in the substrate — but it sits in the *delivery gate*, not the classifier. The substrate does not say whether that window also defines the `acting → stalled` transition or is a separate filter applied after classification.

**6. Known accuracy.** `entities/mikai`: "L4 accuracy at 18.5% on SQLite-era implementation; target ≥60% before user expansion." No page reports a post-SQLite measurement.

## An unreconciled discrepancy

`concepts/thread-state-machine` describes the same layer with a **different, three-state** taxonomy:

> "classifies open threads across a user's wiki, notes, mail, and task lists into states (active / stalled / closed)"

This does not map cleanly onto the six-state lifecycle — `active` would collapse exploring/evaluating/decided/acting. The substrate does not state whether `active/stalled/closed` is a coarser delivery-facing projection of the six-state machine or a competing formulation. Given that the same page decomposes the layer into state estimation / prioritization / delivery policy and places it at S3 in `concepts/second-brain-strata`, the projection reading is plausible — but that is my inference, not something the pages assert.

## Where the substrate is silent

On the actual mechanics of classification, these pages contain nothing:

- **No transition conditions.** Nothing specifies what evidence moves a thread from `exploring` to `evaluating`, or `decided` to `acting`.
- **No feature set or thresholds.** `concepts/thread-state-machine` names "importance × time-decay scoring" for *prioritization*, but no analogous feature specification exists for *state estimation*.
- **No thread-detection method.** Stage 1 of the pipeline ("detect thread") is named but not specified here. The nearest adjacent material is in `sources/2026-07-04-consolidating-multiple-discussion-threads-c6ea03`, which frames thread grouping as kNN + union-find and "entity resolution / record linkage" — but that page is about *consolidating conversation threads*, a different operation from L4 task-thread segmentation, and it does not claim to describe L4.
- **No backward or skip transitions.** Whether `stalled → acting` recovery exists, or whether states can be skipped, is unstated.
- **No arbitration for multi-signal or ambiguous threads.**
- **No definition of `completed`,** which matters given that `concepts/thread-state-machine` cites ChatGPT Pulse's failure — "reminding users of projects they have already completed" — as the exact thing having a state machine is supposed to prevent.

The retrieved pages establish the classifier's *contract* (six states, activity vocabulary in, deterministic rules only, ≥60% accuracy bar) without its *implementation*. If the implementation is written down, it is not in this retrieval set.

### Lane B — serial  _(OK, 55.5s, 7471ch)_

## The vocabulary first — it isn't four states

No retrieved page lists a four-state machine. Two variants appear:

**Six states, with arrows** — `sources/2026-06-18-task-state-awareness-2-0-b2f08c` gives the canonical form under "L4 State Machine":

```
exploring → evaluating → decided → acting → stalled → completed
```

**Five states, as a flat set** — `concepts/noonchi-retrieval-chain` step 4: "assign one of five states: exploring / evaluating / decided / acting / stalled." `concepts/executive-assistant-feed` repeats the same five ("exploring / evaluating / decided / acting / stalled"), as does `concepts/instruction-density-axis` when it refers back to "the same L4 state machine."

So `evaluating` is present in every version and shouldn't be dropped from the question's list; `completed` appears only in the June 2026 formalization source. The substrate doesn't say whether the five-state pages are abridging the six or predate/postdate it — the discrepancy is unresolved in the retrieved pages.

Also worth noting: the arrows in the June source depict a linear chain, which would make `stalled → completed` the only exit from stall. That is almost certainly a display simplification rather than a claim about legal transitions, but no retrieved page gives a transition table, so I can't confirm it either way.

## Where classification sits in the pipeline

Classification is **step 4 of 5** in the noonchi retrieval chain (`concepts/noonchi-retrieval-chain`), which is described there as "the operational definition of L4 task-state awareness":

1. `get_stats` orient — baseline node count, recent ingestion, graph health
2. `search_graph` — semantic search for the current concern
3. `expand_graph` 1-hop — surface adjacent entities, relationships, recent episodes
4. **classify thread state**
5. surface gap + infer next step

Two structural claims follow from that placement. First, classification consumes a retrieved-and-expanded neighborhood, not a raw query — the graph expansion is the evidence base. Second, it feeds forward: `concepts/noonchi-retrieval-chain` states "the retrieval chain produces a thread state classification. The [[concepts/timing-intelligence]] layer uses that classification to decide *when* to surface the result." The comparison page `comparisons/R2_headless_vs_claude_ai_2026-08-27` reports the same dependency in strata terms, quoting `concepts/second-brain-strata`: Sumimasen sits at S4 and depends "on S3 (`concepts/thread-state-machine`) having classified thread state first."

`concepts/instruction-density-axis` adds that this pipeline is invariant: "detect thread → classify state → infer next step" runs identically whether the input is an explicit big-red-button instruction or a pure behavioral trace. "Only the density of the input signal varies; the engine is invariant."

## How threads get formed before they get classified

Detection and classification are separate operations, and the substrate specifies detection more concretely. `sources/2026-07-04-consolidating-multiple-discussion-threads-c6ea03` names the primitive: "**Clustering / thread detection** — kNN plus union-find connected components. The sub-move of determining whether two threads are 'the same' is entity resolution / near-duplicate detection (the same four-tier problem [[entities/graphiti]] solves on entities)."

That gives you an algorithm for *what is a thread*. It gives you nothing about *what state a thread is in*.

## What mechanism does the classification

The retrieved pages never say directly. The strongest signal is indirect, from `sources/2026-06-18-task-state-awareness-2-0-b2f08c`, where the epistemic vocabulary is dropped with a falsifiable revival condition: "O-036 rule-based classifier fails and typed relational edges are genuinely needed for thread detection in L4." That presupposes a **rule-based classifier** as the working assumption for L4 — and makes the epistemic/typed-edge machinery the fallback if rules prove insufficient. The same source records that the activity vocabulary was "adopted as spine of the Intent & Goal Map" for task-state corpora.

But no retrieved page enumerates those rules. There is no feature list, no signal→state mapping, no threshold for any individual state.

The one quantitative hint touching a state name is second-hand and belongs to a different layer. `comparisons/R2_headless_vs_claude_ai_2026-08-27` quotes `sources/2026-04-02-agent-memory-640e67` for the Sumimasen Gate Rules (V1): "48h cooldown per thread, **7–30d stall window**, recency filter, cross-source boost, cap 5/cycle. Deterministic rules only at V1." A 7–30 day window implies stall is at least partly elapsed-time-derived — but that is the *delivery gate's* window for what it will surface, not stated anywhere as the classifier's definition of the stalled state. ## Short answer

The substrate's direct answer to this question lives in one page — `sources/2026-07-01-neural-networks-for-mikai-graph-inference-572b84`, a two-turn Claude thread — and its framing is that **the obvious answer (graph neural networks) is the wrong near-term answer.** The recommended near-term architectures are not GNNs at all.

## Near-term: two label-free approaches

**L3 (graphing layer)**

- **Multi-scale semantic embeddings** — 128/256/512 granularity combined with Reciprocal Rank Fusion; possibly ColBERT-style late-interaction for short transactional segments.
- **Self-supervised structural graph embeddings** — node2vec, Deep Graph Infomax (DGI), or unsupervised GraphSAGE. These encode *topological position* rather than semantics, complementing Voyage's embeddings. The payoff named is concrete: the hybrid weighting currently hand-tuned in FOUNDATIONS §3 (`boost 0.08→0.12`) could be *learned* instead of set by hand.

**L4 (inference layer)**

- **Multivariate Hawkes process, one per thread** — called "the sleeper pick." Each thread's timestamped episode stream is a self-exciting point process; fitted intensity λ(t) says how active the thread is now, decay toward baseline marks the transition into `stalled`, and the 90th-percentile inter-event interval replaces an arbitrary N-day stall window. The argument for it is that parametric Hawkes fits on very little data and is "essentially a zero-LLM statistical model, directly serving the O-036 design philosophy." `concepts/hawkes-process` and `concepts/temporal-point-process` carry the underlying model definitions.
- **Everything else** — gradient-boosted trees (XGBoost/LightGBM) or rule-based, per D-026.

## Long-term: the actual GNN stack, gated on labels

`concepts/temporal-graph-networks` is the fullest treatment. **TGN** (Rossi et al. 2020, per-node memory updated by message passing on each new interaction) and **TGAT** (Xu et al. 2020, time-encoding plus attention over a node's temporal neighborhood) are described as "the architecturally correct model" for `entities/graphiti`'s bitemporal graph — each edge carrying valid-time and transaction-time, edges invalidated rather than deleted (726 invalidated edges noted). The specific gain claimed is *unification*: MIKAI currently handles graph structure (L3) and temporal dynamics (L4) as separate heuristics; TGN would learn one representation over both.

Then **supervised GNN link prediction**, and finally the **PPP RL loop** (already deferred by design spec). The sequencing diagram in that page is explicit:

```
Now:   Hawkes (per-thread, parametric, zero labels)

       + rule-based / GBT per D-026
Later: TGN/TGAT → supervised GNN link prediction → PPP RL loop
```

The gate is the data regime. `concepts/temporal-graph-networks` and the source page both cite ~12,600 nodes and only ~20–30 labeled threads planned for MEMTRACK — a regime the source calls "actively hostile to supervised deep learning." ## Q8. What's the difference between agent memory (persistent) and context management (per-session)?

### Lane A — parallel  _(OK, 69.6s, 8558ch)_

## The substrate's sharpest framing: **query-time synthesis vs. write-time promotion**

The wiki's most direct answer to this question is the split named in `sources/2026-08-09-memory-management-systems-for-claude-a28e30`:

> *query-time synthesis* works well (proven in Claude Projects) but is re-derivation — full-corpus cost per question, nothing persists. *Write-time promotion* requires a query-independent importance function.

That is the whole distinction in one line:

- **Context management (per-session)** is query-time. It re-derives the relevant slice of the corpus on every question, pays full-corpus cost each time, and leaves nothing behind when the session ends.
- **Agent memory (persistent)** is write-time. It commits a durable artifact *before* any question exists — which is why it needs an importance function that does not know the query.

The page's canonical treatment lives at `concepts/query-time-vs-write-time-memory`, which was **not in the retrieved set** — I'm working from the source page's summary of it, not the concept page itself.

## The systems framing: paging vs. the store

`concepts/five-lineages-of-memory` supplies the mechanical version, from Lineage 1 (Memory as Scarcity, 1945–1980s):

> A context window is a working set; context assembly is paging.

Its bequest is the **[[admission-eviction-prefetch]] triad** — "admission (what gets in), eviction (what leaves), prefetch (what to stage before it's asked for)." Under this framing, context management is the pager; agent memory is the backing store it pages from. They are not competing designs; they are two halves of one hierarchy, which is why MIKAI's L1/L2/L3 tiering is listed there as the LLM-era replay of exactly this lineage.

The same page gives the strategic consequence, and it's the most load-bearing claim in the retrieved substrate:

> **Storage and query-triggered retrieval commoditize every generation** (filesystems → databases → desktop search → RAG).
> **Context-triggered judgment — what deserves attention right now — has never commoditized because it has never been solved.**

So: per-session context assembly (query-triggered retrieval) is on the commoditizing side of the line — the page notes RAG "was commoditized within 18 months." Persistent memory only earns its keep on the side that hasn't commoditized: eviction, prefetch, and judgment about what deserves attention unprompted.

## What makes persistence actually work: the dream layer

The 2026-08-09 source is explicit that write-time promotion is not a storage decision but a *pipeline*, and lists the community-converged practices:

2. **"Emit candidates, not commits."** The dream produces a separate candidate store; the input stays intact for review, discard, or rollback.
3. **"Gate promotion with evidence scoring."** OpenClaw's six weighted signals through three threshold gates; only deep-sleep writes to MEMORY.md. The page calls this "the importance function as a staged pipeline."

Point 5 is the feedback edge between the two: per-session retrieval is not just a consumer of memory, it's the training signal that decides what persists.

**Load trigger.** Always-on injection (CLAUDE.md) vs. description-triggered (skills) vs. just-in-time read (memory tool). The page's decision rule follows directly:

> - Stable, always-relevant preferences → CLAUDE.md (always-on load)
> - Task procedures → skill (description-triggered load)
> - Agent-accrued facts → memory file (just-in-time read)

## The deeper cut: who supplies salience

`sources/2026-08-09-memory-management-systems-for-claude-a28e30` argues the lifetime framing is the shallow version. Its central claim is that current systems "conflate two distinct operations under the word 'memory'":

- **Query-time synthesis** — "inference runs at question time; **the question supplies salience**; full-corpus cost per query; nothing persists or compounds."
- **Write-time promotion** — "a standing, **query-independent** decision about which candidate facts get promoted to durable memory."

Under this reading, context management is query-time: the current task tells the system what matters, and when the session ends that judgment evaporates. Agent memory requires deciding importance *before* anyone asks — which is the harder problem, because there's no question to lean on. The source names the failure mode bluntly: systems substitute corpus statistics as a proxy, so on a MIKAI-style corpus "claude/wiki/graphiti out-rank the Atacama proposal, which appears rarely but matters far more."

## What bridges the two

`concepts/sleep-time-compute` names the mechanism: "a background process that analyzes agent trajectories and updates memory stores during idle time, **without a user query pending**." `concepts/crystallization` names the operation: converting a completed chain of work into "a structured durable digest" — volatile → durable. Both exist precisely because per-session context doesn't promote itself.

`sources/2026-04-02-agent-memory-640e67` supplies the working metaphor: `[[entities/letta]]` "uses an OS metaphor — agents page memory in and out like RAM/disk." Context management is paging; memory is disk. Same source gives the cost signature — mem0 at ~1,764 tokens/conversation vs 26,031 for full-context — which is what you'd expect if one is compression-under-pressure and the other is retrieval-from-store.
