Architecture Flow

How data moves from raw capture to action — ingestion, substrate, dream derivations, task-state awareness, surfaces, executors — with the write-back rail that closes the loop.

01Data-flow diagram
02Legend — the five arrows that matter
  • Ingestion → substrate Watchers, pollers, and the drop folder converge on one write path — ingestEpisode() through the WikiAdapter — appending verbatim episodes to wiki.md, never summarizing at capture time.
  • Substrate → dream The dream crons are the only readers of the full 27 MB corpus: nightly narrative, weekly ontology + user-model, monthly compact — compression happens asleep, on a schedule, not at query time.
  • Derivations → L4 The brain never reads raw wiki; hydrator and latent-threads read the ontology (filtered by USER_MODEL) and write proposals to the inbox — Brian's triage is the only path into threads/ and entities/.
  • L4 → surfaces Cockpit, inspector, surfacing, ask, and the Attention Engine all render the same brain state — one attention-owed ranking, five presentations (pull portraits and one Sumimasen-gated push).
  • L4 → executors Nothing executes without an explicit approval tap; every executed action writes back to the ledger and its thread log, so action becomes tomorrow's substrate.

Pink dots mark data in motion; dashed strokes mark proposals and frozen paths. The mikai_llm shim sits beside everything: all LLM calls, both tiers, one provider seam.

    (a) Frozen Neo4j/sidecar stack — 822 MB of infra/graphiti/, docker-compose still in launchd. (b) The catch: it isn't actually dead. mikai_decide still queries :8100 and reads stale wiki-ontology-v1.md, and dream_bootstrap.py lives inside that directory.   • Attention Engine vs cockpit attention head COLLAPSE the scoring
    (a) Two salience computations: cockpit's score_attention_owed() ranks brain/threads; mikai_decide ranks Graphiti search hits + old ontology. (b) Push vs pull are genuinely different jobs — but the ranking shouldn't be, and today the push channel reasons from a frozen substrate. (c) One scorer (cockpit's), two deliveries; the Engine keeps only what's uniquely its own — the Sumimasen delivery-cost gate.
  • decisions/LOG.md COLLAPSE
    (a) Numbered D-op decisions, 66 lines, 4 entries. (b) Zero inbound references from any thread file — nothing navigates by D-op number. (c) Append decisions to the owning thread's log; delete the standalone file.
  • Three surfaces · entities/ · narrative + ontology KEEP
    Cockpit/inspector/surfacing serve different consumers (operator portrait, diagnostic, raw text — COCKPIT_ORGANIZATION_TRADEOFF's portrait-not-dashboard argument holds); revisit only if inspector and surfacing converge on shared panels. entities/ is four curated files powering ENTANGLED-WITH edges and hydrator dedup — costs nothing. Both dream pages have machine consumers (ontology → hydrator/latent-threads; narrative → user_model/tensions), so neither is "one prompt away." Hydrator and latent-threads propose different objects through one inbox; merge their crons, not their code.
